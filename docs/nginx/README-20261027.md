# Nginx Rajacek — perbaikan BESAR-1 + KECIL-8 (audit login 2026-10-27)

File konfigurasi siap pakai: [`rajacek.com-20261027.conf`](./rajacek.com-20261027.conf)
(disiapkan 2026-10-27, **belum diterapkan ke live** — tidak ada edit, reload,
restart nginx, maupun perubahan firewall selama penyusunan).

## 1. Konfigurasi live yang ditemukan (read-only, 2026-10-27)

Sumber: `/etc/nginx/sites-enabled/rajacek.com` (symlink ke
`/etc/nginx/sites-available/rajacek.com`), `nginx -T`, dan `nginx -V`.

- `sites-enabled/` hanya berisi satu entri: `rajacek.com` (symlink). Site
  `default` tidak aktif.
- nginx 1.24.0 (Ubuntu), dibangun **dengan** `http_realip_module` — prasyarat
  perbaikan BESAR-1 terpenuhi, tidak perlu modul tambahan.
- Blok **:443**: `server_name rajacek.com www.rajacek.com`,
  `client_max_body_size 1m`, satu `location /` dengan
  `proxy_pass http://127.0.0.1:8080`, `proxy_http_version 1.1`,
  `Host $host`, `X-Real-IP $remote_addr`,
  `X-Forwarded-For $proxy_add_x_forwarded_for` (APPEND — ini celahnya),
  `X-Forwarded-Proto $scheme`, `proxy_read_timeout 60s`.
  TLS dari Certbot (`fullchain.pem`/`privkey.pem` untuk `rajacek.com`,
  `options-ssl-nginx.conf`, `ssl-dhparams.pem`), sertifikat berlaku s.d.
  19 Jan 2027. **Tidak ada** direktif `real_ip` maupun `set_real_ip_from`
  apa pun di konfigurasi live — tidak ada yang perlu diselaraskan, hanya
  ditambahkan.
- Blok **:80** (koreksi atas deskripsi audit): bukan 404 untuk semua host.
  Isi live adalah dua blok `if ($host = ...)` Certbot yang `return 301`
  untuk `www.rajacek.com` dan `rajacek.com`, plus `return 404` di tingkat
  server. Jadi **404 hanya untuk Host yang tidak cocok** (mis. request
  langsung ke IP / SNI lain); tautan http biasa sudah dialihkan. Blok baru
  menyederhanakan ini menjadi 301 tanpa syarat.
- Tidak ada `location` ACME, webroot, atau rujukan Cloudflare apa pun di
  konfigurasi nginx live (grep `cloudflare|CF-Connecting` di `/etc/nginx/`
  kosong).
- Backup lama di server: `rajacek.com.bak-20261025-k10` — beda dari live
  hanya `proxy_read_timeout` (30s vs 60s live). Tidak dipakai sebagai basis;
  basis edit adalah file live.

## 2. Perubahan baris per baris vs live

### Blok :443 (BESAR-1)

| # | Live | Baru | Alasan |
|---|------|------|--------|
| 1 | — (tidak ada) | Blok `set_real_ip_from` × 22 (15 IPv4 + 7 IPv6) di tingkat server | Daftar resmi Cloudflare, lihat §3 |
| 2 | — | `real_ip_header CF-Connecting-IP;` | Header yang ditulis Cloudflare; hanya dipercaya dari peer di daftar §3 |
| 3 | — | `real_ip_recursive on;` | Telusuri rantai sampai IP pertama bukan trusted proxy |
| 4 | `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` | `proxy_set_header X-Forwarded-For $remote_addr;` | **Kunci perbaikan:** overwrite, bukan append — nilai kiriman klien dibuang |
| 5 | — | `proxy_set_header CF-Connecting-IP $remote_addr;` | Aplikasi membaca header ini pertama; nilainya kini dijamin dari nginx, bukan klien |
| — | Semua sisanya (`server_name`, `client_max_body_size 1m`, `proxy_pass`, `proxy_http_version`, `Host`, `X-Real-IP`, `X-Forwarded-Proto`, `proxy_read_timeout 60s`, seluruh baris TLS + komentar `# managed by Certbot`) | **Tidak berubah, verbatim** | Ubah seminimal mungkin; `X-Real-IP` kini otomatis ikut benar karena `$remote_addr` sudah dikoreksi real_ip |

Catatan mekanisme (kenapa perbaikan ini sah): untuk request via Cloudflare,
peer nginx adalah edge Cloudflare (ada di daftar) → `CF-Connecting-IP`
dipercaya → `$remote_addr` = IP klien asli → kedua header overwrite berisi
IP asli. Untuk request langsung ke origin (melewati Cloudflare), peer tidak
ada di daftar → header kiriman penyerang diabaikan → `$remote_addr` = IP
peer penyerang sendiri → header overwrite berisi IP penyerang yang benar.
Dalam kedua jalur, nilai palsu tidak bisa lolos.

### Blok :80 (KECIL-8)

| # | Live | Baru | Alasan |
|---|------|------|--------|
| 1 | — | `location ^~ /.well-known/acme-challenge/` → `root /var/www/html`, `try_files $uri =404` | Pengecualian ACME, lihat §4 |
| 2 | Dua `if ($host = ...)` + `return 301` + `return 404` tingkat server | `return 301 https://$host$request_uri;` tingkat server | 301 tanpa syarat; satu-satunya perubahan perilaku: Host tak dikenal dulu 404, kini 301 |
| — | `listen 80`, `listen [::]:80`, `server_name` | Tidak berubah | — |

## 4. Setup certbot / renewal live (read-only)

- `/etc/letsencrypt/renewal/rajacek.com.conf`: `authenticator = nginx`,
  `installer = nginx` — **bukan webroot**. Tidak ada webroot yang
  terkonfigurasi di nginx live, dan `/var/www/html/.well-known/` saat ini
  tidak ada (direktori `/var/www/html` sendiri ada).
- Timer `certbot.timer` aktif (renewal 2× sehari, berikutnya 28 Okt 2026
  pagi); sertifikat berlaku s.d. 19 Jan 2027.
- Konsekuensi untuk blok :80 baru: pengecualian ACME di file ini adalah
  **jaring pengaman, bukan jalur renewal live**. Plugin nginx certbot
  menyisipkan lokasi exact-match per token selama renewal lalu menghapusnya;
  lokasi exact-match mengalahkan prefix `^~`, jadi keduanya berdampingan.
  Jalur renewal yang sesungguhnya tetap plugin nginx.

## 5. Temuan firewall (read-only) — risiko residual

- UFW aktif, default `deny (incoming)`, tetapi `80/tcp` dan `443/tcp`
  `ALLOW IN Anywhere` (IPv4 + IPv6). `22/tcp` juga `Anywhere`. Tidak ada
  pembatasan sumber ke rentang Cloudflare di UFW, iptables, maupun nft
  (aturan nft yang terlihat hanya rantai standar UFW).
- Artinya: **jalur langsung ke origin masih mungkin di lapisan jaringan**
  — siapa pun bisa mencapai nginx :443 tanpa lewat Cloudflare.
- Ini **bukan blokir deploy**: setelah overwrite header (§2), request
  langsung tetap tercatat/dithrottle dengan IP peer penyerang yang benar,
  bukan IP palsu. Spoof header sudah tidak berpengaruh. Yang tersisa
  hanyalah: penyerang langsung masih bisa menghabiskan throttle/antifarm
  dengan IP-nya sendiri (sama seperti user sah mana pun) — bukan bypass.
- Opsi pengerasan lanjutan (di luar tugas ini, perlu keputusan koordinator/
  user, karena berisiko memutus akses bila salah): batasi UFW 443 hanya
  dari rentang Cloudflare §3. Jangan dilakukan dalam deploy gabungan ini
  tanpa persetujuan eksplisit.

## 6. Instruksi penerapan untuk koordinator (deploy gabungan)

```bash
# 1. Di server, backup dulu konfigurasi live yang sedang jalan:
sudo cp /etc/nginx/sites-enabled/rajacek.com \
  /etc/nginx/sites-available/rajacek.com.bak-20261027-nginx
# (sites-enabled adalah symlink ke sites-available; cp via path symlink
#  mengikuti target — verifikasi dengan ls -l setelahnya.)

# 2. Salin file baru ke tempatnya (file ini dari repo/docs):
sudo cp rajacek.com-20261027.conf /etc/nginx/sites-available/rajacek.com
#    sites-enabled/rajacek.com sudah symlink ke file itu — bila belum,
#    buat: sudo ln -s /etc/nginx/sites-available/rajacek.com \
#               /etc/nginx/sites-enabled/rajacek.com

# 3. Uji sintaks — JANGAN reload bila gagal:
sudo nginx -t

# 4. Bila lolos, reload (bukan restart):
sudo systemctl reload nginx

# 5. Verifikasi pasca-reload (read-only):
sudo nginx -T | grep -A3 -B3 'real_ip\|X-Forwarded-For'
curl -I http://rajacek.com/            # harap 301 ke https
curl -sk -o /dev/null -w '%{http_code}\n' https://rajacek.com/  # harap 200
```

## 7. Ketidakpastian — wajib dibaca koordinator

1. **Sintaks file baru belum diuji dengan `nginx -t`.** VM worker tidak
   memiliki binary nginx, jadi validasi sintaks hanya bisa dilakukan di
   server pada langkah 3 §6. Jangan reload sebelum `nginx -t` lolos.
2. **Renewal belum terverifikasi pasca-perubahan.** Setelah deploy, jalankan
   `sudo certbot renew --dry-run` dan pastikan lolos; bila dry-run gagal
   karena blok `location` ACME, hapus blok location itu saja (301 murni
   tetap kompatibel dengan plugin nginx, lihat §4) lalu ulangi dry-run.
   Pantau juga renewal nyata pertama setelah deploy dan diff konfigurasi
   sesudahnya (plugin nginx bisa menulis ulang bagian yang ia kelola).
3. **Daftar CIDR adalah snapshot 2026-10-27.** Bila Cloudflare mengubah
   daftar sebelum tanggal deploy, ambil ulang dari kedua URL §3.
4. **Uji spoof pasca-deploy belum dilakukan** (di luar wewenang worker
   read-only ini): koordinator sebaiknya menguji bahwa header
   `CF-Connecting-IP` palsu dari luar Cloudflare tidak lagi mengubah IP
   yang dicatat aplikasi (cek log/monitor trial), dan bahwa request via
   Cloudflare tetap mencatat IP klien asli.
5. File ini tidak mengandung secret/kredensial apa pun (hanya path sertifikat
   publik dan rentang IP publik Cloudflare).

## 8. Koreksi pasca-deploy — return harus di dalam `location /` (2026-10-27)

**Temuan saat verifikasi deploy:** versi pertama file ini meletakkan
`return 301 https://$host$request_uri;` di tingkat server (di bawah lokasi
ACME). Hasilnya: SEMUA path, termasuk `/.well-known/acme-challenge/`,
menjawab 301 — lokasi ACME tidak pernah menangani request apa pun, padahal
`nginx -T` menunjukkan konfigurasi termuat dan `nginx -t` lolos.

**Penyebab (gotcha nginx, terbukti lewat debug log):** `return` di tingkat
server dieksekusi pada fase server-rewrite, SEBELUM location matching.
Buktinya: debug log untuk request ACME hanya mencatat baris
`http request line`, tanpa satu pun baris `test location` — request
dihentikan sebelum fase FIND_CONFIG. Jadi lokasi apa pun di server block
tersebut tidak pernah tercapai selama ada `return` tingkat server.

**Perbaikan yang diterapkan:** `return 301` dipindah ke dalam
`location / { ... }`. Sekarang lokasi `^~` ACME (prefix terpanjang) menang
atas `/` untuk path tantangan, sisanya jatuh ke `location /`.

**Tes akhir pasca-koreksi (dari VPS, 2026-10-27):**
- `/.well-known/acme-challenge/ping.txt` (file sengaja dibuat) → **200**
- `/.well-known/acme-challenge/nope123` (tidak ada) → **404**
- `/` dan path lain di :80 → **301** ke https
- File uji `ping.txt` dan debug log sudah dihapus; konfigurasi termuat
  tidak lagi mengandung `debug80`.

**Catatan yang menggantikan §7 butir 2:** saran "hapus blok location ACME
bila mengganggu renewal" sudah TIDAK berlaku — masalahnya bukan blok
location, melainkan penempatan `return`. Dry-run renewal diulang pada
konfigurasi final (lihat laporan deploy) dan lolos; lokasi exact-match
plugin certbot tetap mengalahkan prefix `^~` bila renewal berjalan.
